# Final Report — Build Instructions

The course final report for **BLG 562E** is `report.md`. Pandoc renders it
to `report.docx`; that DOCX is the deliverable.

## Files in this folder

```
report/
├── README.md             — this file
├── report.md             — main source
├── report.docx           — rendered deliverable (regenerated by pandoc)
├── figures/
│   ├── make_roofline.py  — regenerates fig_roofline.{pdf,png,svg}
│   ├── fig_roofline.{pdf,png,svg}
│   ├── fig_throughput.{pdf,png,svg}
│   ├── fig_speedup.{pdf,png,svg}
```

The figure files come from `poster/figures/` and `poster/diagrams/`
(generated by `poster/figures/make_figures.py` and the TikZ sources).
They are duplicated here so the report builds standalone. PDF and SVG
versions are kept for archival quality; the DOCX pipeline embeds the
PNG versions.

## Build the DOCX

From the `report/` directory:

```powershell
& "C:\Users\talha\.local\pandoc\pandoc-3.10\pandoc.exe" `
    report.md -o report.docx `
    --toc --number-sections `
    --resource-path=".;figures;diagrams"
```

Or, if `pandoc` is on PATH:

```bash
pandoc report.md -o report.docx \
    --toc --number-sections \
    --resource-path=".:figures:diagrams"
```

The output is `report/report.docx`, containing the title page, table of
contents, eight figures (one new roofline plus five matplotlib figures
and two TikZ diagrams from the poster, plus a third TikZ kernel
architecture diagram in §3), and two appendices. The current build is
about 1.7 MB with all nine images embedded as PNG.

### Why PNG and not SVG inside the DOCX

Pandoc needs `rsvg-convert` (from librsvg) to embed SVG into DOCX.
That tool is not available on this Windows host and is non-trivial to
install. PNG embedding works out of the box with Pandoc alone and the
PNGs in this folder are rendered from the same source as the SVGs (300
DPI). The SVG files are kept alongside for archival purposes; if you
later install librsvg you can switch the image extensions in
`report.md` from `.png` to `.svg` and re-render.

## Regenerating the roofline figure

The roofline plot is derived from the Nsight Compute metrics quoted in
`docs/plan.md` (post-refactor profile at N = 10^7). To regenerate:

```bash
cd figures
py make_roofline.py
```

The script also prints a summary table of the derived numbers
(arithmetic intensity, achieved GFLOPS, GB/s, and percentage of peak
FP32) for verification:

```
Peak compute :  2490.0 GFLOPS
Peak DRAM    :   128.0 GB/s
Ridge point  :   19.45 FLOPS/byte

kernel                   AI     GFLOPS       GB/s     % peak
mc_naive             1783.2       68.5       0.04       2.8%
mc_shared             446.5     1977.3       4.43      79.4%
mc_antithetic         290.7     1901.6       6.54      76.4%
```

If you update the source numbers (e.g. re-profile on a different GPU),
edit the `PEAK_GFLOPS`, `PEAK_BW_GBPS`, and `KERNELS` dictionary at the
top of `make_roofline.py` and re-run.

The script writes `fig_roofline.pdf`, `fig_roofline.png`, and
`fig_roofline.svg` in one pass.

## Regenerating the other figures

The other five figures (`fig_throughput`, `fig_speedup`,
`fig_speedup_bars`, `fig_convergence`, `fig_nsight_metrics`) are
generated by `poster/figures/make_figures.py` from
`results/benchmark.csv`. After re-running the benchmark sweep,
regenerate them:

```bash
cd ../poster/figures
py make_figures.py
cp fig_*.pdf ../../report/figures/
cp fig_*.png ../../report/figures/
```

## Verification checklist

1. `report.docx` builds without errors.
2. Open `report.docx` in Word. Every figure renders (no missing-image
   placeholders).
3. Validation table (§5.1), profile table (§5.4), and roofline numbers
   (§5.5) reconcile with the source CSV and `docs/plan.md` log entries.
4. `mc_shared` and `mc_antithetic` sit near the FP32 compute ceiling on
   the roofline. `mc_naive` sits well below both ceilings (§6.3
   discusses why this is the correct visual interpretation of atomic
   contention).
